# Level Editor

## Summary

In-game визуальный редактор комнат внутри `rooms.html` как **инструмент ideation для новых комнат** (не миграции существующих): drag-and-drop стен, врагов, спавна, двери и ключа, lazy-spawn триггеры, мгновенный запуск симуляции в том же view — чтобы пробовать варианты "что если поставить...", видеть плотность буллетов на правленой геометрии и находить дизайны, которые трудно представить из кода. Существующие 5 комнат остаются в TS и редактируются как сейчас.

---

## Problem Frame

Сейчас 5 кампанейских комнат уже зашиплены через цикл TS+HMR — workflow работает для **фиксации того, что уже придумано**. Узкое место — на шаге раньше: придумывание новых комнат. Соло-разработчик пишет, что у неё "планы грандиозные, но фантазии не хватает", и хочется инструмент, в котором **новые идеи рождаются в процессе тыкания**, а не сначала проектируются в голове.

Три конкретные болевые точки, из которых складывается ideation-friction:

1. **Слепое выставление координат.** Невозможно понять, как стена реально ложится в композицию, пока не скомпилируешь и не запустишь — это убивает "а что если?" эксперименты. Каждая попытка стоит 5–10 секунд переключения контекста, поэтому пробуют меньше вариантов.
2. **Сложность по коду не читается.** Глядя на список врагов в TS, нельзя понять, "много" это буллетов или "мало" — плотность видна только в проигрывании. Это значит, что баланс комнаты нельзя итерировать в дизайн-фазе, только проверять постфактум.
3. **Микро-правки слишком дороги.** Подвинуть моба на 50 px стоит open-IDE + find-line + edit-number + HMR — активационная энергия выше самой правки. В ideation-режиме это критично: ты хочешь попробовать 10 вариантов расположения, а делаешь 2.

Что Editor должен дать поверх существующего workflow: **визуальный ideation-loop "drag → play → пощупать → drag → play"**, где новая комната рождается через эксперимент, а не через код. Existing 5 комнат остаются в TS — редактор их не трогает.

---

## Key Flows

- F1. Создать новую комнату в редакторе
  - **Trigger:** Дев в `rooms.html` нажимает F3 (edit-mode) на пустом draft-слоте или существующем draft'е.
  - **Actors:** Solo developer.
  - **Steps:**
    1. Edit-mode UI открывает пустую комнату (или последний draft) на пустом canvas со spawn-точкой по центру и сеткой.
    2. Дев drag-rectangle рисует стены, click-stamp размещает врагов из toolbar, расставляет дверь / ключ / pendingEnemies.
    3. Mid-tweak: Play → видит как буллеты летят → паузит → подвинул → опять Play.
  - **Outcome:** Новая комната в working state, готова к финальной проверке и export'у.
  - **Covered by:** R1, R2, R3, R4, R5, R13.

- F2. Test-play изменённой комнаты не выходя из редактора
  - **Trigger:** В edit-mode дев нажимает "Play".
  - **Actors:** Solo developer.
  - **Steps:**
    1. Симуляция запускается с текущей версии комнаты прямо в этом же view.
    2. Игра идёт нормально (буллеты летят, враги атакуют, AI работает).
    3. Дев в любой момент паузит — возвращается в edit-mode с возможностью продолжить или рестартануть от спавна.
  - **Outcome:** Видна плотность буллетов, поведение врагов на новой геометрии.
  - **Covered by:** R6, R7.

- F3. Сохранить изменения обратно в код
  - **Trigger:** Дев доволен правками, нажимает "Export".
  - **Actors:** Solo developer.
  - **Steps:**
    1. Редактор сериализует текущее состояние комнаты.
    2. Изменения попадают в git-tracked файл комнаты (формат — решение планирования).
    3. После следующего рестарта `pnpm dev` правленый код доступен в обычной игре.
  - **Outcome:** Правка зафиксирована под git diff.
  - **Covered by:** R8, R10, R11.

## Requirements

**Edit-mode UI**
- R1. Горячая клавиша **F3** внутри `rooms.html` переключает игровой и edit режимы для текущей комнаты. Переключение мгновенное, без перезагрузки страницы. (F1 = dev-menu, F2 = perf-meter, Esc/Tab = pause — F3 свободна.)
- R2. В edit-mode симуляция заморожена: буллеты, враги, таймеры не двигаются; ввод игрока игнорируется.
- R3. В edit-mode видна сетка для снапа координат. Стандартный шаг сетки — **10 px**; снап включён по умолчанию, тогл-кнопка отключает его для пиксель-точных правок.
- R4. Properties panel показывает свойства выделенной сущности и позволяет их править: HP / флаги (`dropsKey`, `startsAggressive`, `ignoresWalls`) для врагов; `requiresKey` и `nextRoomId` для двери; `dashable` для стен; координаты для всех.
- R13. В edit-mode middle-mouse drag панит view, scroll wheel зумит (диапазон 0.5×–2.0×). Камера не следует за игроком (игрок заморожен). Кнопка "Center on spawn" возвращает камеру к точке спавна. Нужно для камерных комнат (Room 4 = 8000×700, Room 5 = 1600×1200) — иначе дальние сущности недоступны.

**Размещаемые сущности (MVP)**
- R5. Редактор поддерживает размещение, перетаскивание и удаление следующих сущностей:
  - **Стены (AABB)** с флагом `dashable`. Создание — **drag-rectangle** от точки клика до отпускания мыши.
  - **Враги:** Turret, Watcher, Hunter — с их per-type опциями. Размещение — **click-to-stamp из toolbar** (выбран тип врага → клик в позицию на canvas).
  - **Spawn-точка** игрока (одна на комнату, не удаляется).
  - **Door** с настройками `requiresKey` и `nextRoomId`.
  - **`initialKey`** (статически размещённый ключ).
  - **Размер комнаты** (width × height) — через drag за края или числовые поля в Properties panel.
  - **Lazy-spawn триггеры (`pendingEnemies`):** тип врага + точка спавна + значение `triggerX`. Визуально — вертикальная пунктирная линия в позиции `triggerX` через всю высоту комнаты + маркер врага в точке спавна. Drag за линию меняет `triggerX`; drag за маркер меняет позицию спавна.
  - **Удаление:** Delete или Backspace для выделенной сущности. Spawn-точка не удаляется (на её попытку — toast "spawn cannot be deleted").
- R5a. **Пассивные поля Room shape, не редактируемые визуально в MVP, но сохраняемые через import/export 1-в-1:** `ambientBullets` (поле плавающих буллетов — Room 1 core combat), `worldLabels` (текстовые надписи в мире — INFECTED ZONE в Room 1), wall-флаги `infected` / `mergeLeft` / `mergeRight` (визуальная тонировка / швы стен). Properties panel позволяет править их как числовые поля при выделении соответствующей сущности, но drag-handle и UI создания/удаления — out of scope MVP.

**Live test-play**
- R6. Из edit-mode одной кнопкой запускается симуляция комнаты в её текущем (правленом) состоянии прямо в том же view — без перехода на другую страницу и без потери редакторского состояния.
- R7. Во время play горячая клавиша пауза-toggle возвращает в edit-mode. Из edit-mode доступны две команды: "Resume" (продолжить с того же кадра) и "Restart from spawn" (перезапустить комнату от точки спавна). **При Resume bullet / particle / ring pools очищаются** — Resume сохраняет позиции врагов, игрока, awareness state, но снимает projectiles, чтобы избежать буллетов внутри изменённой геометрии (например, после drag стены на траекторию буллета).

**Связь с существующими комнатами**
- R8. Редактор **не импортирует** существующие 5 кампанейских комнат (`room1`..`room5`) и не редактирует их. Они остаются в TS как сейчас и правятся через код. Editor создаёт **новые** комнаты, которые добавляются в кампанию через явный шаг integration (см. R11). Импорт-миграция существующих 5 комнат — explicit non-goal MVP, отложено до подтверждения формата на новых комнатах.
- R9. Tutorial-комнаты (`src/tutorial/room0..room3`) и Sentinel (Room 5) — out of scope как и раньше; их фаза-машины и state-машины остаются в коде. Создание новых boss-комнат через редактор тоже не входит в MVP (см. вопрос Sentinel-precedent в Resolve-Before-Planning).

**Persistence и Export**
- R10. Изменения автосохраняются в `localStorage` как черновики на каждую комнату. Перезагрузка страницы не теряет правки. **Черновики помечены бейджем "DRAFT"** в header редактора + цветной border вокруг изменённых сущностей. При конфликте с обновлённым кодом (mtime / hash `room*.ts` новее, чем draft) показывается баннер `Draft from <дата>, code is newer` с двумя кнопками: `Keep draft` (продолжаем с черновиком, поверх свежего кода) / `Revert to code` (черновик удаляется из `localStorage`).
- R11. Кнопка "Export" формирует артефакт, попадающий в git-tracked код комнаты (конкретный формат — решение планирования). До export'а правки живут только в `localStorage`.
- R12. Кнопка "Revert" сбрасывает редактор к исходному состоянию комнаты (как в коде), отбрасывая черновик в `localStorage`.

## Acceptance Examples

- AE1. **Covers R1, R2, R6.** Дев открывает редактор на пустой draft-комнате, click-stamp размещает 4 турели и Watcher (greenfield композиция в стиле Room 3) → нажимает Play → буллеты летят. Не нравится плотность → пробел / F3 пауза → тащит одну турель из (250, 250) в (400, 400) → опять Play → видит как сразу изменился поток. Никакой перезагрузки страницы, цикл "drag → play → drag" в одном view.
- AE2. **Covers R3, R4.** Дев выделяет стену → меняет в properties panel её ширину с 30 на 60 px → стена расширяется на сетке со шагом 10 px. Тогл "Snap" выключается → можно выставить ширину 53 px для пиксель-точной правки.
- AE3. **Covers R5, R7.** Дев проектирует новый корridor-style room: длина 4000 px, ставит 3 lazy-spawn триггера для hunter'ов (вертикальные пунктирные линии в `triggerX = 1000 / 2000 / 3000`, маркеры спавна в правой части каждого сегмента). Play → играет, паузит на середине → перетаскивает второй триггер с 2000 на 2400 → "Restart from spawn" → видит новую динамику с самого начала.
- AE4. **Covers R10, R11.** Дев в течение часа экспериментирует с новой комнатой: 15 итераций drag/play. Закрывает вкладку браузера, не нажав Export → открывает заново → весь прогресс на месте, бейдж "DRAFT" в header. Нажимает Export → новая комната попадает в git-tracked файл (`src/rooms/roomN-new.ts` или эквивалент по формату), виден `git diff`.
- AE5. **Covers R10.** Дев работает над draft'ом → делает `git pull` который обновляет другую часть `room*.ts` (не связанную с её draft'ом) → возвращается в редактор → видит баннер "Draft from <date>, code is newer" → нажимает "Keep draft" → её работа продолжается, баннер исчезает.
- AE6. **Covers R12.** Дев экспериментально пересоздаёт всю draft-комнату — добавляет 10 стен, перемещает всех врагов → передумала → нажимает Revert → редактор возвращается к последнему export'нутому состоянию (или к пустой комнате если export'а ещё не было), `localStorage` черновик удалён.

## Success Criteria

- Соло-разработчик может **родить как минимум одну новую комнату через ideation-loop в редакторе**, которую ей трудно было бы спроектировать в коде слепо. Метрика — субъективная: "я нашла дизайн через тыкание, который не предсказала бы заранее".
- Цикл "drag entity → play → пощупать буллеты → drag → play" в редакторе занимает < 5 секунд на итерацию (одно изменение → видимая разница). Через TS+HMR этот цикл невозможен в принципе — там нет интерактивного тыкания, только compile + run.
- Editor запускается из landing page / `rooms.html` без отдельных setup-шагов; работа сохраняется автоматически между сессиями (`localStorage` черновики).
- Downstream planning может дойти до конкретных файлов / схем / API без необходимости угадывать поведение или scope.

## Scope Boundaries

- **Импорт-миграция существующих 5 кампанейских комнат** (room1–room5). Они остаются в TS-коде, редактор их не трогает. Можно добавить как post-MVP, когда формат докажет себя на новых комнатах.
- **Создание boss-комнат через редактор.** Sentinel и любые будущие state-machine боссы — захардкожены в коде. Редактор обращается с боссами как "place opaque sprite", но в MVP даже это не нужно — boss-комнаты целиком авторятся в коде.
- Tutorial Room 0 с её фаза-машиной (markers → dash gate → combat dummy) — не редактируется. Tutorial-комнаты 1–3 — тоже не на старте; их геометрия проще, можно добавить позже без переделок архитектуры.
- Pickup-планировка (HP / Shield / ScoreBoost / Breaker) — pickup'ы в rooms сейчас не размещаются вручную, спавнятся только через bullet-drop в sandbox. Не добавляем в редактор.
- Граф цепочки комнат / визуальный flowchart кампании. `nextRoomId` правится как поле в properties panel, без визуализации связей между нодами.
- Отдельная страница `editor.html` как CAD-инструмент (Approach B из brainstorm).
- Шеринг уровней, мод-поддержка, UI для не-кодеров.
- Создание новых типов врагов через редактор — только размещение существующих архетипов (Turret / Watcher / Hunter).
- Undo/redo на старте. Добавится, если возникнет дёшево из архитектуры черновиков; иначе после MVP.
- Интеграция с sandbox-режимом — редактор живёт только в `rooms.html`.

## Key Decisions

- **Edit-mode встроен в `rooms.html` (Approach A+C, не отдельная страница).** Главная боль — отсутствие визуальной обратной связи во время дизайна и дороговизна микро-правок. Отдельный CAD удлинил бы цикл "правка → проверка", воспроизводя текущую боль с TS+HMR. Встраивание в игру решает оба пункта одним механизмом.
- **Live play без выхода из view.** Кнопка "Play" в edit-mode запускает симуляцию прямо тут же, а не открывает другую страницу / iframe. Это критично для "пощупать плотность буллетов" — переключение страниц вернуло бы боль (3).
- **Импорт через runtime-state, не парсинг TS.** Редактор перехватывает результат текущих `buildRoomN()` функций (они выдают готовый `Room` объект), а не парсит исходники TS. Проще, надёжнее, не ломается от рефакторинга `room*.ts`.
- **Sentinel — спрайт-плейсхолдер, не редактируемая сущность.** Атаки и фазы босса — крупная state machine, экспонировать их в редакторе нет смысла. Позиция и размер арены — да, остальное остаётся в `sentinel.ts`.
- **Tutorial-комнаты — out of scope.** Tutorial Room 0 — это фаза-машина, не данные. Tutorial 1–3 простая геометрия, но их добавление потребовало бы развести "tutorial" и "campaign" registries в редакторе. Дёшевле отложить.
- **`localStorage` для черновиков, отдельная команда Export для коммита.** Сохраняет цикл "поэкспериментировать без боязни сломать код" + явный момент "теперь это правда". Без явного Export нет автоматической записи в файлы — пользователь сохраняет контроль над `git diff`.
- **MVP — только новые комнаты (greenfield).** Editor создаёт новые комнаты с нуля, не импортирует существующие. Решение принято на основании ответа пользователя: главная боль — ideation новых комнат, а не миграция. Если формат и UX оправдают себя на greenfield, импорт существующих 5 комнат добавится post-MVP. Это сразу убирает риск "1-в-1 preservation" и весь связанный test plan из критического пути.
- **Формат хранения новых комнат = runtime JSON в `src/rooms/*.json`.** Existing `room*.ts` файлы остаются как есть. Новый `src/lib/room-from-json.ts` loader парсит JSON в `Room` объект; `rooms-game.ts` принимает оба варианта (TS-built или JSON-loaded). Два формата сосуществуют, что приемлемо для greenfield-MVP — codegen TS дороже (TS-printer, синхронизация стиля с существующими файлами), а единый JSON для всех потребовал бы миграции existing 5, что мы как раз отложили. Hot-reload работает через Vite-native HMR для JSON.
- **pendingEnemies spawn shape — точка + опциональный random-Y range.** Discriminated union: `spawn: { kind: 'point', x, y } | { kind: 'randomY', x, yRange: [number, number] }`. Покрывает базовый случай (точка) и Room-4-style (рандом по вертикали на фиксированной x-колонне). В редакторе: drag маркера спавна = "point" mode; правая кнопка / context menu на маркере → "convert to random-Y range" → у маркера появляются две ручки сверху и снизу для y1/y2. Прямоугольная область отложена — не нашли use case в текущем контенте.
- **Export mechanism — Vite dev-server plugin.** Маленький Vite plugin регистрирует endpoint `POST /__editor-save` (или похожий internal-only path), который принимает `{ path, json }` и пишет файл в `src/rooms/*.json`. Click "Export" → запрос → файл записан → Vite HMR подхватывает (если игра запущена). UX: один клик, файл сразу в `git diff`. Плата: ~50 строк TS в новом `vite-plugin-editor.ts` + регистрация в `vite.config.ts`. Endpoint доступен только на dev-сервере, в prod-сборку не попадает.
- **Boss-комнаты — навсегда code-authored, не в формате редактора.** JSON-схема редактора **не** содержит поля под Sentinel или других state-machine врагов. Новые boss-комнаты (если появятся) пишутся в TS так же, как сейчас Room 5. Это самый чистый MVP-scope: редактор делает то, что хорошо умеет делать (geometry + базовые враги для ideation), и не пытается покрыть state-machine territory. Если post-MVP всё-таки понадобится — формат расширяется опциональным полем без breaking change.

## Dependencies / Assumptions

- `Room` shape в `src/rooms/room.ts` остаётся стабильной для новых комнат, которые редактор создаёт (минимум `walls` / `enemies` / `door` / `spawnX/Y` / `pendingEnemies` / `initialKey` / `width` / `height`). Existing 5 комнат могут продолжать использовать дополнительные поля (`ambientBullets`, `worldLabels`, wall flags) — редактор их не трогает.
- Существующие враги (Turret / Watcher / Hunter) уже data-shaped: позиция + опции конструктора. Создание Sentinel из редактора не входит в MVP.
- `pendingEnemies` для **новых** комнат проектируется заново как чистые данные (формат — на планировании). Existing `pickHunterSpawn` в Room 4 не трогается; рефакторить legacy callback'и не нужно, поскольку редактор их не импортирует.
- F1 dev-меню (god-mode + teleport) сосуществует с редактором — edit-mode использует другую клавишу, не F1.
- Pause-механизм во время play в edit-mode = пауза существующей рантайм-симуляции, не запуск отдельного "редакторского" движка. Все существующие системы (camera, particle pools, audio ducking, performance meter F2) должны корректно переживать "freeze frame".
- Tone.js / audio — не затрагивается; edit/play режимы используют ту же ленивую инициализацию, что обычная игра.
